# アイタス (AITAS) - グランドデザイン

> 2026-02-28 策定 / 2026-03-16 更新 / Gemini・Claude 共同開発用マスタードキュメント

## 1. プロダクトビジョン

アイタス (AITAS) は、単なる記録ツールではなく、AIキャラクターとの対話を通じて「タスク管理の挫折」を「共同作業」に変える、**感情駆動型のマネジメントアプリ**です。

- **コアコンセプト**: 「管理する」から「一緒にこなす」へ。
- **最重要ポリシー**: ユーザーを絶対に責めない。途切れても「また始めれば大丈夫」。
- **ターゲット**:
  - タスク管理に挫折しがちな層
  - プライバシー重視のパワーユーザー
  - 多忙なマルチタスカー

## 2. 技術スタック & アーキテクチャ

| カテゴリ | 技術 | 備考 |
|---|---|---|
| Frontend | React Native (Expo 54), React Navigation 7, React Native Paper | Material Design 3 |
| Language | TypeScript (strict mode) | |
| Storage | **expo-sqlite** | ローカルデータ保存、UUID管理（将来のクラウド同期を見据え） |
| AI Engine (Primary) | **Gemini 2.5 Flash API** (Google AI Studio) | クラウド優先・ゼロ設定で即利用可能 |
| AI Engine (Advanced) | **Ollama (Llama 4:8b, Gemma3:4b等)** | パワーユーザー向けオプション |
| Deploy | Expo (iOS/Android) / Vercel (Web) | |

### アーキテクチャ方針
- **クラウドファースト**: AI推論はGemini API をデフォルトとし、初回起動から設定不要で使える体験を最優先。
- **ローカルAIはオプション**: 設定画面から有効化。プライバシー重視・カスタマイズ志向のパワーユーザー向け。
- **データはローカル保存**: タスクデータ自体は端末内SQLiteに保持。AI通信のみクラウド。
- **UUID管理**: 将来のクラウド同期・マルチデバイス対応に備え、IDはUUID v4で管理。

## 4. オンボーディング — 自由対話型ヒアリング

初回起動時に選択式アンケートではなく、**AIとの自然な会話**でユーザーを理解する。

### フロー
1. パーソナリティに応じた初回挨拶（時刻考慮）
2. AIが「普段どんなことをしていますか？」と聞く
3. ユーザーが音声 or テキストで自由に話す（仕事、趣味、やりたいこと等）
4. AIが発話を解析し、カテゴリ・ユーザープロファイルを自動生成
5. 提案されたカテゴリ一覧をユーザーが確認・調整して確定
6. オンボーディング完了フラグ → メイン画面へ遷移

### ユーザー発話の解析例
```
「IT企業でエンジニアやってて、副業でWebデザインもやってる。
 趣味はゲームと筋トレ。プログラミングの資格も取りたい」

  → 💼 本業（エンジニア）   [strict]
  → 💻 副業（デザイン）     [strict]
  → 🎮 ゲーム              [relaxed]
  → 💪 筋トレ              [normal]
  → 📚 資格勉強            [normal]
  → 📦 雑務                [normal] ← 全ユーザーに自動付与
```

### ユーザープロファイル（学習用に保存）
```typescript
interface UserProfile {
  id: string;
  onboardingRaw: string;      // 元の発話テキスト（全会話トランスクリプト）
  occupation: string | null;   // "ITエンジニア"
  sideWork: string | null;     // "Webデザイン"
  interests: string[];         // ["ゲーム", "筋トレ"]
  goals: string[];             // ["プログラミング資格"]
  ageGroup: string | null;     // "20代" (発話から推定 or 未取得)
  createdAt: string;
}
```

活用先: 適応型スケーリングのパーソナライズ、AIの応答の具体性向上、リスケジュール時の判断材料。

## 5. カテゴリシステム

### 5.1 カテゴリの定義
```typescript
interface TaskCategory {
  id: string;                 // UUID
  name: string;               // "本業", "筋トレ", etc.
  icon: string;               // MaterialCommunityIcons名
  color: string;              // テーマカラー
  sortOrder: number;          // 並び順
  isDefault: boolean;         // カテゴリ未指定タスクの振り分け先
  scalingWeight: 'strict' | 'normal' | 'relaxed';
  parentId: string | null;    // 親カテゴリID（階層構造用）
}
```

### 5.2 scalingWeight（スケーリング重み）
| weight | 意味 | 適用例 | スコアへの影響 |
|---|---|---|---|
| `strict` | 期限厳守、未完了はスコアに大きく影響 | 仕事、勉強 | 高 |
| `normal` | 標準的な扱い | 家事、健康、雑務 | 中 |
| `relaxed` | 気楽でOK、未完了でもスコアに影響しにくい | 趣味、ライフゴール | 低 |

### 5.3 カテゴリ操作
| 操作 | 方法 |
|---|---|
| 追加 | 新規作成 or 既存カテゴリを複製して編集 |
| リネーム | タップで名前・アイコン・カラーを編集 |
| 複製 | 長押し or メニューから「コピーして作成」→ 設定を引き継ぎ |
| 削除 | 配下タスクの移動先を選んでから削除 |
| 並び替え | ドラッグ&ドロップ |

**複製のユースケース**: 「仕事」→ コピー →「本業」「副業」にリネーム

### 5.4 「雑務」カテゴリ（全ユーザー共通）
- 全ユーザーに必ず付与される特殊カテゴリ
- カテゴリ未指定タスクの自動振り分け先
- リネーム可（「今日の用事」「その他」等に変更OK）

### 5.5 階層構造（サブカテゴリ）
カテゴリは `parentId` を持ち、親子関係を表現できる。

例: 「本業」(親) → 「報告書作成」「企画会議」(子)

サブカテゴリはAIによる自動提案で蓄積される（→ セクション14参照）。

## 6. スーパーゴール（上位目標）

### 6.1 概要
長期的な目標をカテゴリに紐づけて管理し、個々のタスクがどのゴールに貢献するかを可視化する。

### 6.2 データモデル
```typescript
interface SuperGoal {
  id: string;                 // UUID
  categoryId: string;         // 紐づくカテゴリ
  title: string;              // "AWS資格取得"
  description: string;        // ゴールの詳細
  targetDate: string;         // 目標期限 (ISO 8601)
  status: 'active' | 'completed' | 'archived';
}
```

### 6.3 タスクとの関連
- タスクは `superGoalId` フィールドでスーパーゴールにリンク
- AIレビュー時にゴール直結タスクは特別な診断ラベル「🎯 ゴール直結」を付与
- Glow Tier で green（高優先）に分類

### 6.4 操作
| 操作 | 方法 |
|---|---|
| 作成 | カテゴリごとにスーパーゴールを追加 |
| 編集 | タイトル・説明・期限・ステータスを更新 |
| 削除 | ゴールを削除（紐づくタスクのリンクは解除） |
| 完了/アーカイブ | ステータスを切り替え |

### 6.5 今後の拡張候補
- ゴールへの貢献度スコア（タスク完了数 / マイルストーン進捗率）
- ゴール期限からの逆算によるタスク優先度自動調整
- ゴール達成率のダッシュボード表示

|---|---|

|---|---|

| その他の自然言語 | AIとの対話（アドバイス、質問応答等） |

### 7.5 「すべて見る」展開ビュー
ホーム画面内で1日の全タスクを縦一覧表示。**重要度に応じてタスクの表示サイズが変わる**。

```typescript
function calcDisplayScore(task: Task, category: TaskCategory): number {
  let score = 50;
  if (task.priority === 'high') score += 30;
  if (task.priority === 'medium') score += 15;
  if (category.scalingWeight === 'strict') score += 20;
  if (category.scalingWeight === 'normal') score += 10;
  if (task.dueDate === today) score += 20;
  if (task.dueDate === tomorrow) score += 10;
  return clamp(score, 10, 100);
}
```

| スコア | フォントサイズ | 視覚効果 |
|---|---|---|
| 80〜100 | 20px | **太字**、カテゴリアイコン付き |
| 50〜79 | 16px | 通常表示 |
| 20〜49 | 13px | やや薄い色 |
| 10〜19 | 11px | 薄い色、圧縮表示 |

**「押しつぶして消す」操作**: 小さいタスクをスワイプ→「今日はやめる」で翌日送り。残りタスクの表示が拡大。
**「集中モード」ボタン**: スコア30以下を一括で翌日送り。
**全部大事なとき**: 全タスクのスコアが均一 → 文字サイズの差がほぼなくなる。

### 7.6 ケアモードバナー
ケアモード中はホーム画面上部にバナーを表示し、軽めのタスク推奨を促す。

### 7.7 全タスク完了時
```
🎉 今日のタスク、全部終わり！
AI: 「お疲れさま！明日の分、少し準備する？」
[ 明日の計画を見る ]
```

## 8. タスク一覧画面 — スワイプページ設計

### 8.1 ページ構成
```
[ 📋 今日 ] → [ 🔥 緊急 ] → [ 💼 本業 ] → [ 💻 副業 ] → [ 📚 資格 ] → [ 📦 雑務 ]
    横断ビュー（固定）               カテゴリ別（ユーザー定義順）
```

| ページ | 内容 | 固定/可変 |
|---|---|---|
| 1: 今日 | 今日やることの横断一覧 | 固定（常に先頭） |
| 2: 緊急 | 期限3日以内の横断一覧 | 固定 |
| 3〜: カテゴリ別 | ユーザーが作ったカテゴリ順 | 可変（並び替え可能） |

### 8.2 各ページ共通のUI
- フィルタ: all / active / completed
- 検索: そのカテゴリ内のみ検索
- 完了カウント: そのカテゴリの進捗表示
- タスク追加: カテゴリが自動セットされた状態で追加
- スワイプで完了切替

### 8.3 カテゴリが多い場合
ドットインジケータ + タップでカテゴリ一覧オーバーレイ → 直接ジャンプ可能。

### 8.4 フローティング 🎤 ボタン + スマートコマンド
タスク一覧画面に常駐する音声/テキスト入力ボタン。AIが自然言語を理解してアクションを実行。

| 発話例 | AIの動作 |
|---|---|
| 「AWS問題集どこ？」 | 📚 資格勉強ページへ自動スワイプ + 該当タスクをハイライト |
| 「筋トレ追加して」 | 💪 筋トレカテゴリに新規タスク作成 |
| 「今日何が残ってる？」 | 📋 今日ページへジャンプ |
| 「報告書おわった」 | 該当タスクを完了処理 |
| 「副業のやつ全部見せて」 | 💻 副業ページへ自動スワイプ |

ジャンプ時はスワイプアニメーション + 該当タスクがパルスで光る演出。

## 10. 「今日は無理！」ボタン — 理由ベース設計

### 10.1 押下時に理由を1タップで聞く
```
🗓 予定が変わった     → スコア影響なし、タスク移動のみ
😴 今日は休みたい     → ケアモード1日
😰 ちょっとしんどい    → ケアモード3日
   やっぱりやる！     → キャンセル
```

### 10.2 リスケジュール処理
- 今日の未完了タスク全てを翌日に移動
- `rescheduleCount` をインクリメント（リスケ回数を追跡）
- `originalDueDate` を保持（元の期限を記録）
- `reschedule_history` テーブルに理由・対象タスクID・日時を記録

### 10.3 ケアモード
| トリガー | 期間 | スコアへの影響 |
|---|---|---|
| 😴 休みたい | 1日 | スコア上限50にクランプ |
| 😰 しんどい | 3日 | スコア上限50にクランプ |

#### ケアモードの自動解除
- 完了率が2日連続50%以上 → 通常モードに復帰
- ユーザーが「今日の調子は？」で「好調」を選択 → 即復帰
- 有効期限切れ → 自動解除
- DB に `careModeExpiresAt` を保存

#### パーソナリティ別ケアモードメッセージ
| パーソナリティ | メッセージ例 |
|---|---|
| standard | 「無理せず、できることから始めましょう」 |
| ゆるアシ | 「今日はゆっくりでOK〜！」 |
| マジアシ | 「回復も戦略です。軽めのタスクから」 |

## 11. ルーティンタスク機能

### 11.1 ルーティンの定義
```typescript
interface RoutineConfig {
  frequency: 'daily' | 'weekdays' | 'weekly' | 'custom';
  customDays?: number[];     // custom時: [1,3,5] = 月水金
  timeSlot?: 'morning' | 'afternoon' | 'evening' | 'anytime';
  streak: number;            // パーフェクト連続達成日数
  bestStreak: number;        // 過去最高
  softStreakDays: number;    // ゆるstreak継続日数
  createdAt: string;
}
```

実装では `isRecurring` + `recurringPattern` ('daily' | 'weekly' | 'monthly') で管理。

### 11.2 ルーティンの作り方
| 方法 | フロー |
|---|---|
| 新規作成 | タスク追加時に「繰り返し」トグル → 頻度選択 |
| 既存タスクから変換 | 長押し → 「ルーティンにする」 |
| AIが提案 | 同じタスクを3日連続で登録 → 「ルーティンにしますか？」 |

### 11.3 AI自動スケジューリング
ユーザーが「筋トレ週3」等とざっくり伝えると、AIが既存スケジュールの負荷を分析し、最適な曜日を提案。

```
入力: 💪 筋トレ 週3
     月   火   水   木   金   土   日
💼  ■■■  ■■■  ■■■  ■■■  ■■■  ·    ·   ← 本業
📚  ·    ■    ·    ■    ·    ■    ·   ← 資格

AI判定: 金・土・日が最も余裕あり
提案: おすすめプラン（金土日）+ 別プラン（月水金の1日おき）
ユーザー: 「おすすめで決定」or「自分で選ぶ」
```

まずは**固定曜日**で実装。将来的に毎週AIが最適配置を提案するモードを追加。

### 11.4 2段階 streak 評価

| streak種別 | 条件 | 表示 |
|---|---|---|
| **パーフェクト** | 指定日を連続で全て達成 | 🔥 |
| **ゆるstreak** | 直近期間の達成率70%以上 | ✨ |

#### 頻度別のゆるstreak基準
| ルーティン頻度 | ゆるstreakの条件 |
|---|---|
| 毎日 (daily) | 7日中5日以上 |
| 平日 (weekdays) | 5日中4日以上 |
| 週1 (weekly) | 直近4週中3週以上 |
| カスタム（例: 週3） | 直近2週の指定回数の70%以上 |

#### 表示の段階
```
🔥🔥🔥  パーフェクト7日以上
🔥🔥   パーフェクト3〜6日
🔥    パーフェクト1〜2日
✨    ゆるstreak継続中（5/7日）
(なし)  基準未満
```

#### AIの反応（途切れた時 — 絶対に責めない）
| パーソナリティ | 反応 |
|---|---|
| standard | 「昨日はお休みでしたね。今日からまた始めましょう」 |
| ゆるアシ | 「大丈夫大丈夫〜！また今日からでOK！」 |
| マジアシ | 「リセットされましたが、再開初日の継続率は高いです」 |

## 12. 適応型スケーリング

### 12.1 カテゴリ別独立スコア
スコアはカテゴリごとに独立して算出。「仕事は絶好調だけど勉強は停滞」のような細かい判定が可能。

### 12.2 スコア算出（3層ハイブリッド）
```
カテゴリ別スコア (0〜100)
│
├─ 定量データ (50%)
│   ├─ ルーティン完了率 × 0.6    ← 主要評価対象
│   ├─ 通常タスク完了率 × 0.3    ← 補助
│   └─ 緊急タスク完了率 × 0.1    ← 参考程度
│
├─ トレンド (30%)
│   ├─ 3日移動平均 vs 7日移動平均（上昇/下降傾向）
│   └─ streak状況（パーフェクト/ゆる/途切れた）
│
└─ 自己申告 (20%)
    ├─ 「今日の調子は？」（好調 +20 / ふつう ±0 / きつい -20）
    └─ 「今日は無理！」の理由に連動
```

### 12.3 動的重み調整（データ不足時）
利用開始直後はデータが不足するため、自己申告の比率を動的に引き上げる。

| データ蓄積期間 | 定量 | トレンド | 自己申告 |
|---|---|---|---|
| 3日未満 | 20% | 10% | **70%** |
| 3〜4日 | 35% | 25% | **40%** |
| 5日以上 | 50% | 30% | 20%（標準） |

### 12.4 streakのスコアボーナス
| streak状態 | ボーナス |
|---|---|
| パーフェクト 7日以上 | +15 |
| パーフェクト 3〜6日 | +10 |
| パーフェクト 1〜2日 | +5 |
| ゆるstreak 継続中 | +5 |
| どちらもなし | ±0 |
| ゆるstreakすら途切れた | -5 |

### 12.5 ケアモード時のスコアクランプ
`isCareMode === true` の間、スコアは **最大50** にクランプされる。

### 12.6 スコア → AIの振る舞いマッピング
| スコア | 状態ラベル | AIの振る舞い |
|---|---|---|
| 0〜25 | `care_needed` | ベビーステップ（5〜10分単位）、タスク数を減らす提案 |
| 26〜50 | `slow_start` | 15〜30分単位の分解、1日3件以内を推奨 |
| 51〜75 | `on_track` | 標準的なサブタスク分解、バランス型提案 |
| 76〜100 | `excellent` | チャレンジ目標の提示、マイルストーン型の大きめタスク |

### 12.7 エッジケース
| ケース | 対処 |
|---|---|
| データ不足（利用開始3日以内） | デフォルト50、動的重み調整適用 |
| カテゴリ内タスク0件の日 | その日はスコア計算から除外 |
| streak 7日以上 | ボーナス+15（最大100キャップ） |

### 12.8 必要なDBカラム
- `completed_at`: タスク完了日時（ISO 8601）→ 7日間完了率算出に必須
- `task_type`: 'routine' | 'normal' | 'urgent' → 重み付け算出に使用

## 13. ポートフォリオタイプ（エネルギー配分）

### 13.1 概要
タスクのエネルギー種別を3つに分類し、AIレビューやスケジューリングの判断材料にする。

### 13.2 分類
| タイプ | 意味 | 例 |
|---|---|---|
| **drive** | 目標達成・成長系 | 資格勉強、企画書、新規開発 |
| **maintenance** | 義務・維持管理系 | 掃除、書類提出、定例MTG |
| **recharge** | 回復・余暇系 | ゲーム、読書、散歩 |

### 13.3 自動推論
タスク追加時にAIがタイトルから自動でポートフォリオタイプを推論。カテゴリ推論と同時に実行される。

### 13.4 活用先
- AIレビューのコンテキスト（drive → 効率重視、recharge → 楽しさ重視）
- 聖域自動検出のトリガー（recharge → 聖域候補）
- 将来的なエネルギーバランス分析

## 14. AIレビューシステム

### 14.1 概要
タスク追加時にバックグラウンドで自動実行される4段階パイプライン。

### 14.2 バックグラウンド推論パイプライン
```
タスク追加
    │
    ▼
[Phase 1] 聖域検出
    │  portfolioType === 'recharge' or キーワード一致 → isSanctuary = true
    ▼
[Phase 2] カテゴリ + ポートフォリオ推論
    │  AIがタイトルから最適カテゴリ・ポートフォリオタイプを判定
    ▼
[Phase 3] サブカテゴリ蓄積 & 閾値チェック
    │  新カテゴリ提案 → pending_suggestions に蓄積
    │  7日以内に同名3回以上 → ユーザーに承認を促す
    ▼
[Phase 4] AIレビュー実行
    │  診断ラベル + Glow Tier + 4軸アセスメント + サブタスク提案
    ▼
[保存] aiReviewCache (JSON) として tasks テーブルに格納
```

`inferenceStatus` で状態管理: `pending` → `completed` / `failed`
アプリ起動時に `pending` 状態のタスクをリトライ。

### 14.3 AIレビュー結果 (v2)
```typescript
interface AiReviewResult {
  diagnosis: {
    label: string;          // "🎯 ゴール直結", "🔧 デイリーケア" 等（プリセット）
    description: string;    // タスク性格の説明
    hint?: string;          // アドバイス
  };
  glowTier: 'green' | 'blue' | 'gray';
  assessments?: {
    necessity: 'good' | 'improve';
    feasibility: 'good' | 'improve';
    decomposition: 'good' | 'improve';
    efficiency: 'good' | 'improve';
  };
  suggestedSubTasks?: string[];
  reviewMode?: 'improve' | 'enjoy';
  isSanctuary: boolean;
  sanctuaryMessage?: string;
  reviewedAt: string;       // ISO 8601
  version: 2;
}
```

### 14.4 Glow Tier（視覚的重要度）
| Tier | 色 | 条件 |
|---|---|---|
| **green** | 緑 | スーパーゴール直結、セルフケア、必要性が高い |
| **blue** | 青 | 標準的なタスク、分解可能 |
| **gray** | 灰 | 必要性が低い、要検討 |

### 14.5 4軸アセスメント
| 軸 | 評価 | 意味 |
|---|---|---|
| necessity | good / improve | このタスクは本当に必要か |
| feasibility | good / improve | 実行可能か（時間・リソース） |
| decomposition | good / improve | 適切に分解されているか |
| efficiency | good / improve | より効率的な方法はないか |

### 14.6 reviewMode
| モード | 適用 | AIの視点 |
|---|---|---|
| `improve` | drive / maintenance タスク | 効率・改善を重視 |
| `enjoy` | recharge / sanctuary タスク | 楽しさ・リラックスを重視 |

## 15. 聖域（Sanctuary）システム

### 15.1 概要
ユーザーにとって大切な余暇・リラックス系タスクをAIの最適化対象から保護する仕組み。

### 15.2 自動検出トリガー
1. `portfolioType === 'recharge'`
2. 既に `isSanctuary === true` にフラグ済み
3. タイトルが `sanctuaryKeywords` に一致

### 15.3 聖域キーワード
設定画面からユーザーがカスタマイズ可能。DB の `settings.sanctuary_keywords` に JSON 配列で保存。

### 15.4 聖域タスクへのAI対応
- AIレビューで最適化・効率化の提案をしない
- `reviewMode: 'enjoy'` が適用される
- 専用の `sanctuaryMessage` で肯定的なコメントを付与
- ケアモードのスコアクランプ対象外

## 16. サブカテゴリ自動提案システム

### 16.1 概要
AIがタスク名からサブカテゴリの候補を検出し、一定回数以上蓄積されたらユーザーに承認を促す。

### 16.2 データモデル
```typescript
interface PendingSuggestion {
  id: string;               // UUID
  taskId: string;            // 提案元タスク
  suggestedTagName: string;  // 提案されたサブカテゴリ名
  reason: string;            // 提案理由
  createdAt: string;
}
```

### 16.3 閾値ロジック
- 7日以内に同じ `suggestedTagName` が **3回以上** 蓄積 → ユーザーに承認UIを表示
- 承認 → `parentId` 付きの新カテゴリとして作成
- 却下 → 該当する `pending_suggestions` を削除

## 17. AIタスク・リファイナー（目玉機能）

### 17.1 概要
ユーザーが入力した抽象的なタスクを、カテゴリ別スコアに基づきAIが自動的に最適化。

### 17.2 1タップ・プレビュー
- AIの提案（分解されたサブタスク群）をプレビューカードで表示
- 1タップで親タスク + サブタスクを一括登録
- 不要なサブタスクの個別除外も可能

### 17.3 分解専用リクエスト
`getDecompositionOnly()` で軽量にサブタスク提案のみを取得可能（フルレビューなし）。

## 19. ハイブリッドAI設計

### 19.1 接続フロー
```
ユーザー入力
    │
    ▼
[AI接続モード判定] ← 設定画面で選択
    │
    ├─「cloud」(デフォルト)
    │    └→ Gemini 2.5 Flash API（設定不要、即利用可能）
    │
    ├─「local」(上級者向け)
    │    └→ Ollama 接続チェック
    │         ├─ 接続OK → ローカル推論（プライバシー保護）
    │         └─ 接続NG → エラー表示 + クラウドへの切替を提案
    │
    └─「hybrid」(実装済み)
         └→ Ollama優先（3秒タイムアウト）→ 失敗時 Gemini に自動フォールバック
```

### 19.2 クラウドAI (Gemini) — デフォルト
- API: Google AI Studio (Gemini 2.5 Flash)
- 特徴: ゼロ設定、安定性高、モバイル含む全環境で動作
- 接続テスト: 設定画面からワンタップで確認可能

### 19.3 ローカルAI (Ollama) — オプション
- ホスト: ユーザーが設定画面で指定（デフォルト: `http://localhost:11434`）
- モデル: Llama 4:8b, Gemma3:4b（または同等）
- 有効化: 設定画面 > 「AIエンジン」 > 「ローカルAI (上級者向け)」
- 接続テスト: 設定画面からワンタップで確認可能

### 19.4 コンテキスト管理
- チャット履歴: 直近20件をAIに送信
- コンテキスト種別: `home`（ホーム画面）/ `review`（レビュー画面）でプロンプト切替
- 全履歴はDBに永続化
