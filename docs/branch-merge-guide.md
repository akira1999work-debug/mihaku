# ブランチマージガイド（EdenQuest）

## ブランチ構成

```
main（本番）← develop（開発統合）← feature/xxx（機能開発）
```

---

## いつdevelopを自分のブランチに取り込むか

| タイミング | 緊急度 | 理由 |
|---|---|---|
| developに**全体に影響する変更**が入った時（リネーム、設定変更など） | 高 | 放置するとほぼ確実にコンフリクトする |
| developに**自分が使うファイル**への変更が入った時 | 高 | 同じファイルを触っているとマージが複雑になる |
| featureブランチの作業が**1週間以上**続いている時 | 中 | 差分が大きくなる前に取り込む |
| featureブランチを**developにマージする直前** | 必須 | 最新状態でテストしてからマージする |
| 特に大きな変更がなく、**数日で終わる作業**の場合 | 低 | 完了時に1回取り込めばOK |

---

## やり方

### 自分のブランチにdevelopを取り込む

```bash
# 1. developを最新にする
git checkout develop
git pull

# 2. 自分のブランチに戻る
git checkout feature/xxx

# 3. developの変更を取り込む
git merge develop

# 4. コンフリクトがあれば解消してコミット
```

### featureブランチの作業が終わったら

```bash
# 1. まずdevelopを取り込む（上の手順）
# 2. 動作確認
# 3. developにマージ
git checkout develop
git merge feature/xxx
git push
```

---

## コンフリクトが起きたら

1. `git status` でコンフリクトしているファイルを確認
2. ファイルを開いて `<<<<<<<` `=======` `>>>>>>>` の箇所を修正
3. `git add` して `git commit`
4. 分からなければチームに相談（無理に解消しない）

---

## やってはいけないこと

| NG | 理由 |
|---|---|
| developに直接コミットする | レビューなしで本番に近い環境が壊れる |
| mainに直接プッシュする | 本番環境に未テストのコードが出る |
| コンフリクトを適当に解消する | 他の人の変更を消してしまう可能性がある |
| 長期間developを取り込まない | マージ時の地獄が待っている |

---

## まとめ

**迷ったら「developを取り込む」でOK。こまめにやるほどマージは楽になる。**
